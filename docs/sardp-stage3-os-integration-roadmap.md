# SARDP Stage 3: 実OS統合 詳細ロードマップ

`sardp-roadmap-post-poc.md`のStage 3を、Windows→macOS→Debian(GNOME)の順で着手する前提で展開したもの。この段階からはClaude CodeのRemote Controlセッション(実GPU・実ディスプレイ・実OS権限にアクセスできる、開発者自身のマシン)での作業になる。

## 共通方針

- **検証方法がここまでと根本的に変わる**。M1〜Stage 2は「ループバックQUIC+CI環境で完結する自動テスト」で進められたが、実キャプチャ・実入力注入は実ディスプレイ・実GUIセッションが要るため、`cargo test`だけでは検証しきれない。各OSのマイルストーンは「自動テストで検証できる部分」と「手動スモークテストでしか確認できない部分」を最初から分けて計画する。
- **3 OSは互いに独立**。並行着手も可能だが、今回は指定どおりWindows→macOS→Debian(GNOME)の順で1つずつ区切る。
- **仕様側の既存決定を前提にする**: Part 7(OS Integration)、DR-012(Wayland方針)、Part 3(プロセス分離アーキテクチャ)、DR-036(永続化エンコーダパイプラインの必要性)。
- **永続化エンコーダパイプライン(DR-036)は3 OS共通の宿題**として最後に別枠で扱う。キャプチャ経路はOSごとに違うが、「フレームごとに`ffmpeg`を起動しない」という要件自体は共通。

## Windows

### 3W-1: 在席(attended)キャプチャ・エンコード基盤

まずここを「動くもの」の到達点にする。SYSTEM権限・無人アクセスは3W-2に分離。

**キャプチャ**: DXGI Desktop Duplication API(`IDXGIOutputDuplication`)。Windows.Graphics.Captureより低レベルだが、ダーティリージョンが`DXGI_OUTDUPL_FRAME_INFO`から直接取れる(Part 8の「変化がなければ送らない」要件に直結)のと、RDP代替製品での実績が豊富な点を優先する。Rustバインディングは公式`windows`クレート。

**エンコード**: キャプチャ結果はDXGIテクスチャ(GPU上)としてそのまま得られるので、CPUへ読み戻さずMedia Foundation Transform(MFT)のH.264ハードウェアエンコーダへ直接渡す経路を組む(NVIDIA環境ならNVENCを`windows`クレート経由で直接叩く経路も検討、Part 6のTier 1に相当)。ここがDR-036の「永続化パイプライン」の実体そのものになる——per-frameプロセス起動をやめるだけでなく、GPU→CPUコピーも避けられるのが実利。

**入力注入**: `SendInput()`(キーボード・マウス)。

**既知の制約(Part 7に既述)**: UAC昇格ダイアログ・ログイン画面はSecure Desktop上にあり、通常権限プロセスからは映らない・操作できない。3W-1の範囲では「ログイン済みのユーザーセッションを、同じユーザー権限のプロセスから覗く」ところまでとし、Secure Desktop越え(3W-2の領分)は別立てにする。DRM保護コンテンツは黒画面になり得る(想定どおりの挙動として確認するに留める)。

**受け入れ基準**: 実デスクトップの変化がクライアント側に表示され、キーボード・マウス操作が実際にWindows側へ反映されること。DR-036のglass_to_glass_usを、per-frame ffmpeg spawn方式(現行PoC)と比較して実測すること。

### 3W-2: 無人アクセス(SYSTEM権限・セッション注入)

Part 3のプロセス分離アーキテクチャ(ネットワーク処理=低権限、ポリシー判定=特権、キャプチャ・入力注入=ユーザーセッション内)を、Windowsでは具体的に**Windowsサービス(SYSTEM権限)がセッション列挙(`WTSEnumerateSessions`)+`WTSQueryUserToken`+`CreateProcessAsUser`でユーザーセッション内にキャプチャエージェントを注入する**という形で実装する。これはPart 3の設計がそのまま当てはまる箇所で、他のRDP代替製品も同じパターンを採る。

ログイン画面・UAC昇格ダイアログのキャプチャ(Secure Desktopの扱い)もここで着手する。

**受け入れ基準**: ユーザーがログアウトした状態からでも接続でき、ログイン画面の操作・ログイン後の画面遷移が継続して見えること。

## macOS

### 3M-1: 在席キャプチャ・エンコード基盤

**キャプチャ**: ScreenCaptureKit(macOS 12.3+)。旧`CGWindowListCreateImage`/`AVCaptureScreenInput`は非推奨のため使わない。ScreenCaptureKitはSwift APIが主であり、Rustの直接バインディングは成熟していないため、**薄いSwift/Objective-Cシムを書いてRustからFFIで呼ぶ**構成を先に決めてから着手する(`objc2`系クレートで直接叩く案もあるが、初回実装はシム経由の方が近道になりやすい)。

**重要な制約——最初に踏むこと**: ScreenCaptureKitの利用には**画面収録(Screen Recording)のTCC権限**がユーザーの明示操作(システム設定でのダイアログ承認)で必要になる。これはコード署名・Entitlement次第でダイアログの出方が変わり、サイレント付与はApple のセキュリティモデル上できない。3W-1着手前に、まず「権限が無い状態から、ダイアログが正しく出て、承認後にキャプチャが動く」という最小限の一連の流れを検証してから本実装に入ること。DR-012でWaylandについて書いた「同意を毎回求める設計思想と無人接続は根本的に相性が悪い」という論点が、macOSでもそのまま当てはまる。

**エンコード**: VideoToolbox(Apple純正のハードウェアエンコーダAPI)。ScreenCaptureKitの出力(`CMSampleBuffer`/`IOSurface`)と相性が良く、Windows同様CPUコピーを避けた経路が組める。

**入力注入**: `CGEvent`系API(`CGEventCreateKeyboardEvent`/`CGEventCreateMouseEvent`)。こちらは**アクセシビリティ(Accessibility)権限**という別のTCCゲートが要る。画面収録権限とは独立に許可が必要な点に注意。

**受け入れ基準**: 3W-1と同様。加えて、TCC権限が無い状態からの初回起動フローが破綻しないこと(クラッシュせず、権限待ちであることが分かる形で待機・再試行できること)を確認する。

### 3M-2: 無人アクセスの検討(未確定)

macOSはWindowsのSYSTEMサービスに相当するクリーンな「特権昇格して他ユーザーセッションに入り込む」経路が標準的に用意されていない。TCC権限はログインユーザーのセッションに紐づく前提が強く、無人アクセス(ログアウト状態からの接続)を実現する一般的な方法は現時点で確立していない。**ここは「実装タスク」ではなく「実現可能かどうかの調査」から始める**。3W-1が動いた後、実機で権限モデルを検証してから、着手するかどうかを改めて判断する。

## Debian(GNOME)

Part 7・DR-012で既に方針は決定済み: **独自コンポジタは作らず、Mutter(GNOME)が提供するリモートデスクトップ用D-Busポータルに連携する。** これは他の2 OSと設計思想が異なる点で、SARDP側は生のキャプチャコードを書くのではなく、**コンポジタが用意している「リモートデスクトップ・ポータル」というAPIのクライアントになる**。

### 3G-1: Wayland経路(xdg-desktop-portal RemoteDesktop/ScreenCast)

- `org.freedesktop.portal.ScreenCast`(画面共有)+`org.freedesktop.portal.RemoteDesktop`(入力注入)のD-Busインターフェースをセッションバス経由で呼び出す。Rust側は`zbus`クレートを使う。
- 画面データは**PipeWire**経由で渡される(ポータルがPipeWireのノードIDを返し、こちらがそこに接続してフレームを受け取る)。`pipewire-rs`クレートを使う。
- **入力注入はポータル自身が提供する**(`NotifyPointerMotion`/`NotifyKeyboardKeycode`等のD-Busメソッド)。Windows/macOSのような生のOS APIを別途叩く必要がなく、この点はGNOME経路の方がシンプル。
- **同意の永続化**: DR-012で触れた`restore_token`(ポータルが対応していれば、初回承認後は次回から同意ダイアログを省略できる)。在席接続はこの方式に統一する。無人接続はスコープ外のまま(DR-012どおり)。

### 3G-2: X11フォールバック

GNOME on Xorgセッション(まだ一定数残っている構成)向けに、XDamageでのダーティリージョン取得+XTestでの入力注入を別経路として用意する。`x11rb`クレートを使う。ポータルが使えない(Xorgセッションではポータルの一部機能が制限される、またはそもそもXorgセッションで起動している)場合のフォールバックと位置付ける。

### 3G-3: ハードウェアエンコード

VAAPI(Intel/AMD、`libva`バインディング経由)またはNVENC(NVIDIA、Windows/macOSと共通のSDK)。ディストリ・GPUベンダーの組み合わせが多岐にわたるため、まずVAAPIを主軸にし、動作確認できたハードウェアから対応を広げる形にする。

**受け入れ基準(3G-1〜3G-3共通)**: Waylandセッションでポータル経由の画面表示・入力操作が動くこと。同意ダイアログが初回のみ出て以降は`restore_token`で省略されること。Xorgセッションでもフォールバック経路で同等に動くこと。

## 3 OS共通の宿題: 永続化エンコーダパイプライン(DR-036)

Stage 2の実測(EC2上、`glass_to_glass_us`が150〜300ms、内訳のほぼ全てがffmpeg起動コスト)で裏付けられたとおり、現行PoCの最大のボトルネックはプロトコル(`transport_us`、実測2〜84μs〜ms オーダーで既に予算内)ではなく、**フレームごとに新規`ffmpeg`プロセスを起動している点**にある。

3W-1/3M-1/3G-1〜3のいずれでも、キャプチャ経路の実装と同時に「エンコーダをストリームの生存期間中ウォームに保つ」設計に置き換わるはずなので、DR-036の課題は各OSの作業の**副産物として解消される**想定にする。独立したタスクとして別途起こす必要はない。ただし、置き換え後に改めてM6の測定ハーネス(`transport_us`/`glass_to_glass_us`)を実行し、`glass_to_glass_us`側も含めてPart 8の目標値(LAN 50ms/WAN 150ms)にどこまで近づいたかを、OSごとに記録しておくこと。

## 進め方の確認

3W-1から着手する。各サブマイルストーン(3W-1→3W-2→3M-1→3M-2→3G-1→3G-2→3G-3)の完了ごとに、これまでと同様に一度立ち止まって報告する形を維持する。ただし今回はRemote Controlセッションでの作業になるため、報告の形(ZIPアップロードでの差分確認)が引き続き有効かどうかは、3W-1着手時に改めて確認する。
