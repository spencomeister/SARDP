# SARDP メッセージスキーマ v0.1(設計経緯つき)

Secure Adaptive Remote Desktop Protocol(仮称 SARDP)のワイヤフォーマット草案と、そこに至るまでの設計判断の記録。
「なぜこの形になったか」を残すことを目的とするため、採用案だけでなく棄却案と棄却理由も記載する。

- 文書バージョン: v0.1(草案)
- 状態: レビュー中。実装しながら修正する段階
- ALPN: `sardp/1`

---

## 第1部 設計の経緯

### 1. 初版の骨子

出発点は「RDPの操作性、VNCより高い画質と応答性、TLS 1.3、デフォルト拒否」を目標にした構成だった。

- 制御チャネル: TLS 1.3 / TCP(認証、セッション管理、入力、クリップボード、ファイル転送)
- 映像チャネル: QUIC / UDP(画面差分、動画フレーム、カーソル、再送制御)
- 画面転送: タイル差分と動画圧縮のハイブリッド、状況に応じて切替
- 独自暗号は作らず TLS 1.3 / 既存コーデック / OS標準認証基盤に乗る

この段階で正しかった判断は「実績ある暗号・コーデックに乗る」「デフォルト拒否」「チャネル分離」の3点。以降のレビューでもここは変えていない。

### 2. 第1回レビューでの主な変更

#### 2.1 入力チャネルがTCP側にある矛盾 → QUIC単一コネクションへ

初版では入力イベントが制御チャネル(TCP)に載っていた。TCPは1パケットの損失で後続すべてが待たされる(Head-of-Line blocking)ため、低帯域・損失環境で最も遅延が増えるのはTCP側になる。「画面が混雑しても操作遅延が増えにくい」という目標と正面から矛盾していた。

対応として、QUIC単一コネクションに統合し、ストリーム単位で役割を分ける構成に変更。

- 認証・セッション管理・ファイル転送: 信頼性付きストリーム
- 入力: 専用ストリーム
- 映像: ストリームまたはDatagram(この時点では未確定)
- TCP+TLSはQUICが通らない環境向けのフォールバックに格下げ

副次効果として、2コネクション構成で必要になる「映像チャネルがどのセッションに属するかの証明」(チャネルバインディング)問題そのものが消えた。

#### 2.2 タイル差分+動画のハイブリッド → 初期版は単一動画エンコーダ

ハイブリッド方式は方式としては王道だが、切替境界のちらつき、二重のレート制御、領域判定など、開発コストの大半を食う。初期版は全画面を単一の動画エンコーダに通し、QPマップ(品質マップ)で文字領域を優遇する方式に変更。静止領域はスキップブロックになりビットをほぼ消費しないため、実質的に差分転送と同等の効率が出る。Parsec、Moonlight/Sunshine、Chrome Remote Desktopが概ねこの系統。

あわせて、文字の滲みの主因がクロマサブサンプリング(4:2:0)にあることを仕様上明記し、4:4:4対応または補助レイヤーの方針を持つことにした。

#### 2.3 その他この回で追加された論点

- キャプチャ層の仕様化(Windows: Desktop Duplication / Windows.Graphics.Capture、macOS: ScreenCaptureKit、Linux X11: XDamage、Wayland: PipeWire+ポータル)
- 入力仕様の第1段階昇格: scancodeとkeysymの併送、`TextInput` の独立メッセージ化、IME方針、座標系の正規化
- リプレイ対策の焦点化: 一般論のnonceではなく「0-RTT禁止」と「再接続トークンの短命・一回限り」に絞る
- 接続モデルの明記: 初期版は直接接続またはVPN経由。リレー導入時はリレーを信頼せず、認証と暗号化はエンドツーエンド
- クリップボードの遅延取得方式(形式一覧のみ通知し、貼り付け時に実データを要求)
- プライバシー機能(在席/無人の区別、接続中表示、画面ブランク、透かし)
- 監査ログのハッシュチェーンとNTP前提

### 3. 第2回レビューでの主な変更

#### 3.1 「キーフレームはストリーム、中間フレームはDatagram」の破綻

P/Bフレームは直前のフレームを参照するため、Datagramで中間フレームが1枚落ちると次のキーフレームまで参照チェーンが壊れ続ける。「キーフレームだけ確実に届ける」では不十分と判明。

さらにQUIC Datagramは断片化できず、1 Datagramは実効1,200バイト前後。数十KBの映像フレームを載せるにはアプリ層でフラグメント化と欠落時のフレーム全破棄を自作することになる。

結論: 初期版は映像もすべて信頼性付きストリームで送る。Datagram化は第2段階で、LTR(Long-Term Reference)またはIntra-refreshによる回復手段、NACK、フレーム分割の実装とセットで、実測に基づいて判断する。

#### 3.2 輻輳制御はQUICスタック任せにできない

quiche、quinn、msquicなど既存QUIC実装の輻輳制御はCUBIC/BBR系のスループット指向で、リアルタイム映像向けのGCC/SCReAM系は載っていない。現実解は、QUIC層の輻輳制御は緩く効かせつつ、アプリ層でエンコーダの目標ビットレート・解像度・FPSを制御する二重構造。このためにクライアントからの `TransportFeedback` メッセージがプロトコルに必要になった。

#### 3.3 エンコーダ能力Tierとフォールバックラダー

QPマップと4:4:4のハードウェア対応はまだらで、フルに使えるのは実質NVENC搭載機のみ。能力ネゴシエーションに基づくTierを定義した。

| Tier | 内容 |
|---|---|
| 1 | ハードウェア4:4:4 + ROI/QPマップ(最適化扱い) |
| 2 | ハードウェア4:2:0 + QPマップ + 文字用補助レイヤー |
| 3 | ハードウェア4:2:0のみ。静止検知後に同領域を高品質フレームで更新 |
| 4 | ソフトウェアエンコード。解像度・FPS制限あり |

初期版の現実的な標準はTier 2または3。4:4:4は仕様上必須にしない(macOS・AMD・Intel環境で利用範囲が狭くなるため)。

#### 3.4 OS制約の明文化

- Windows: UAC・ログイン画面はSecure Desktop上にあり、無人接続にはSYSTEMサービス+ユーザーセッション内エージェントの構成が必須。DRMコンテンツの黒画面、デスクトップ切替検知も明記。
- Wayland: ポータルは毎回の明示同意を要求する思想のため、無人接続と矛盾する。初期版は在席接続のみ、またはrestore tokenが使える環境のみに限定し、完全な無人接続はスコープ外と明記。
- フレーム取得は固定タイマーではなくOSのフレーム到着イベント駆動。変化がなければ映像を送らない。

#### 3.5 サーバーのプロセス分離

ネットワークに面するコードとSYSTEM権限のコードを同じプロセスに置かない。

```text
[ネットワークプロセス] 低権限: QUIC終端、TLS、メッセージ解析、認証
        │ 認証済みIPC
[セッションブローカー] 特権: ポリシー判定、セッション管理、強制切断、監査ログ
        │ OS固有IPC
[セッションエージェント] ユーザーセッション内: キャプチャ、エンコード、入力注入
```

パーサーとTLS終端を非特権プロセスに隔離することで、プロトコル実装の脆弱性がシステム乗っ取りに直結しない構造にする。ワイヤフォーマットはスキーマ定義(長さ前置型)とし、パーサーのファジングをCIに組み込む。

#### 3.6 その他この回の決定

- カーソルはクライアント側でローカル描画(サーバー映像からは除外)。マウス移動の体感遅延をRTT非依存にする。
- 秘密鍵はTPM / Secure Enclave / OSキーチェーンに保存。鍵登録(エンロール)手順を定義する(管理者登録 / ワンタイムコード / TOFU)。ユーザー認証とデバイス識別を分離。
- ログはハッシュチェーンに加え、チェーン先頭ハッシュの定期的な外部アンカリング。
- バージョニングは固定バージョン+Capabilityフラグ交渉。未知の必須メッセージは切断、未知の任意メッセージは無視。
- 実装前に測定ハーネス(フレーム生成時刻の画面埋め込み、E2E遅延自動計測、tc netemによるネットワーク再現)を先に作る。目標値: LAN glass-to-glass 50ms以下、WAN 150ms以下。

### 4. 第3回レビュー(スキーマ化)での修正

#### 4.1 「RESET_STREAMで古いフレームを破棄」の矛盾

全フレームが逐次参照チェーンを構成する以上、次のIDRまでどのフレームも不要にならない。途中のフレームをRESETすれば参照チェーンが壊れ、Datagram方式で避けたかった問題が形を変えて戻る。

修正: 全信頼性方式の輻輳対応は、輸送中のフレームを捨てることではなく、送信元(エンコーダ)で新規フレームの生成を止めること。

```text
feedback / QUIC送信バッファ滞留を監視
   ↓ 滞留が閾値超過
キャプチャ済みフレームをエンコードせず破棄(frame dropping at source)
   ↓ さらに悪化
目標ビットレート・解像度・FPSを段階的に低下
```

エンコードしていないフレームは参照されないため、チェーンは壊れない。よって初期版の映像ストリームは長寿命1本で確定。フレームごとのストリーム生成とRESETは、第2段階でLTR/Intra-refreshによる参照チェーンの張り替えを導入するときに再検討する。

#### 4.2 スキーマ化で炙り出された未決定事項と、その決定

| 事項 | 決定 |
|---|---|
| クロック同期 | 単調時計+`TimeSync` 往復によるNTP風オフセット推定をプロトコルに追加。壁時計はワイヤに載せない |
| 認証の署名対象 | TLSエクスポーター値を含むトランスクリプトへの署名(チャネルバインディング必須) |
| ストリームの自己識別 | QUICストリーム番号に意味を持たせられないため、各ストリーム先頭1バイトで種別を宣言 |
| シリアライゼーション | 構造化ヘッダ(FlatBuffers等)+生バイト列ペイロードの分離構造。映像・ファイルのゼロコピーを維持 |
| IME途中状態 | `TextInput`(確定)とは別に `ImeComposition`(未確定文字列)をメッセージ枠として予約 |
| scancode正規化 | USB HID Usage IDに統一。W3C UI Events codeの対応表を流用 |

## 第2部 確定した設計方針(サマリ)

1. トランスポートは最初からQUIC単一コネクション。TCP+TLS 1.3はフォールバック。
2. 初期版の映像は、単一動画エンコーダ+全信頼性ストリーム1本+送信元フレームドロップ。Datagram+LTR回復は第2段階で実測比較。
3. エンコーダはTier 1〜4のフォールバックラダーで能力交渉。4:4:4は必須にしない。
4. キャプチャ層・座標系・IME・`TextInput` を第1段階仕様に含める。カーソルはクライアント側ローカル描画。
5. 0-RTTは初期版で無効。将来許可する場合も読み取り専用操作のみ。再接続トークンは短命・一回限り、セッションID単独での再接続は禁止。
6. 接続モデルの初期版は直接接続またはVPN経由。リレー導入時もエンドツーエンド暗号を維持。
7. サーバーは3プロセス分離(ネットワーク低権限 / ブローカー特権 / セッションエージェント)。
8. 監査ログはハッシュチェーン+外部アンカリング+NTP前提。秘密鍵はハードウェアバックエンド保管、エンロール手順を定義。
9. 認可はデフォルト拒否。権限はビットフラグのPermissionSetとして認証結果で確定通知。
10. 実装より先に測定ハーネスを作り、方式判断は実測で行う。

## 第3部 メッセージスキーマ v0.1

### 3.1 規約

```text
バイト順        : リトルエンディアン
可変長整数      : QUIC varint (RFC 9000 §16)
文字列          : UTF-8、長さ前置
時刻            : マイクロ秒、送信者の単調時計基準
                  (壁時計は監査ログのみ。プロトコル上は単調時計+オフセット推定)
ID空間          : frame_id, event_id, request_id はストリームごとに独立、0起点単調増加
バージョン交渉  : QUIC ALPN = "sardp/1"。プロトコル内にはバージョン番号を持たず、
                  機能差はすべてCapabilityフラグで表現
未知の要素      : 未知のCapability → 無視
                  未知のメッセージ種別 → 種別番号の最上位ビットで
                  「無視可」「切断必須」を区別
```

### 3.2 ストリームプロローグ

新規ストリームを開く側は、先頭1バイトで種別を宣言する。

```text
0x01 control    (双方向・セッションに1本・最初に開く)
0x02 input      (クライアント→サーバー・1本)
0x03 video      (サーバー→クライアント・初期版は1本)
0x04 feedback   (クライアント→サーバー・1本)
0x05 clipboard  (双方向・要求ごと)
0x06 file       (双方向・転送ごと)
```

不変条件: 未認証状態で control 以外のストリームが開かれたら即切断。この検証はネットワークプロセス(低権限)が最初に行う。

### 3.3 メッセージエンベロープ(全ストリーム共通)

```text
Envelope {
    length   : varint      // type+payloadの長さ
    type     : u16         // 最上位ビット=1なら「未知でも無視可」
    payload  : bytes
}
```

長さ上限はストリーム種別ごとに定義する。パーサーに到達する前に異常入力を落とすため。

| ストリーム | length上限 |
|---|---|
| control | 64 KiB |
| input | 1 KiB |
| video | 8 MiB |
| file | 1 MiB |

### 3.4 ハンドシェイク(controlストリーム)

```text
ClientHello {
    client_name    : string
    client_version : string
    capabilities   : [CapabilityId]     // 例: CURSOR_LOCAL, IME_COMPOSITION, ...
    auth_methods   : [AuthMethod]       // PUBKEY, PASSWORD_MFA, ...
}

ServerHello {
    server_name    : string
    server_version : string
    capabilities   : [CapabilityId]
    auth_required  : [AuthMethod]       // サーバーが受理する方式
    auth_challenge : bytes(32)          // ランダム
}

AuthPubkey {
    user_id     : string
    device_id   : string                // ユーザー認証とデバイス識別の分離
    public_key  : bytes
    signature   : bytes
    // 署名対象 = "SARDP-auth-v1" || auth_challenge
    //          || TLS-Exporter("sardp auth", 32)   ← チャネルバインディング
    //          || hash(ClientHello || ServerHello)
}

AuthResult {
    status          : enum { OK, MFA_REQUIRED, DENIED }
    reason_code     : u16               // 監査ログと共通のコード体系
    session_id      : bytes(16)         // OK時のみ
    reconnect_token : bytes             // 短命・一回限り。有効期限を含む
    granted_permissions : PermissionSet // ビットフラグ:
        // VIEW / INPUT_KEYBOARD / INPUT_MOUSE / CLIP_READ / CLIP_WRITE
        // / FILE_UP / FILE_DOWN / ADMIN
}
```

補足:

- パスワード等の追加方式は `AuthPassword` / `AuthMfaResponse` として同じ枠組みで追加する(本版では枠のみ)。
- チャネルバインディングにより、中間者経由の認証転送を構造的に防ぐ。
- 0-RTT early dataでは control ストリームの認証以外を一切受け付けない(初期版は0-RTT自体を無効)。

### 3.5 セッション確立と能力(controlストリーム)

```text
DisplayConfig {                    // サーバー→クライアント。構成変更時にも再送
    monitors : [{
        monitor_id    : u8
        x, y          : i32        // 仮想デスクトップ物理ピクセル座標
        width, height : u32
        scale_percent : u16        // 論理DPIスケール(表示参考用)
        rotation      : enum { R0, R90, R180, R270 }
        primary       : bool
    }]
}

EncoderConfig {                    // サーバー→クライアント。適用中の設定を通知
    codec         : enum { H264, H265, AV1, ... }
    profile       : u16
    chroma_format : enum { C420, C422, C444 }
    bit_depth     : u8
    width, height : u32
    max_fps       : u16
    tier          : u8             // 能力Tier番号。診断・ログ用
}

DisplayCapabilities {              // クライアント→サーバー。デコード能力の申告
    codecs : [{
        codec, profile, bit_depth, chroma_format
        max_width, max_height, max_fps
        hardware_acceleration : bool
    }]
}

TimeSync {                         // どちらからでも。feedbackストリームでも可
    t1 : u64                       // 送信時刻
    t2 : u64                       // 相手の受信時刻(応答時に充填)
    t3 : u64                       // 相手の送信時刻(応答時に充填)
}                                  // NTP同様に往復でオフセットとRTTを推定
```

エンコーダ側の能力(QPマップ、ROI、B-frame、intra_refresh、long_term_reference の可否)はサーバー内部の選定材料であり、ワイヤにはTier番号と適用結果(EncoderConfig)のみを流す。

### 3.6 映像(videoストリーム)

```text
VideoFrame {
    frame_id       : varint
    flags          : u8            // bit0: IDR / bit1: 参照フレーム / bit2: 解像度変更
    capture_ts     : u64           // サーバー単調時計
    encode_done_ts : u64           // エンコード遅延の切り分け用
    width, height  : u32           // 解像度変更フレームのみ必須
    payload_len    : varint
    payload        : bytes         // コーデックビットストリーム
                                   // (Annex-B / AVCC等の形式はcodecごとに固定して別紙定義)
}

CursorShape {
    cursor_id      : u16
    width, height  : u16
    hotspot_x, hotspot_y : u16
    format         : enum { RGBA8888, ... }
    pixels         : bytes
}

CursorUpdate {
    cursor_id      : u16           // 形状はIDでクライアント側キャッシュ参照
    x, y           : i32
    visible        : bool
}
```

設計意図: `capture_ts` と `encode_done_ts` を最初からワイヤに載せることで、クライアント側の受信・デコード完了・表示時刻と合わせ、パイプラインのどこで遅延が出ているかをフィールドで切り分けられる(測定ハーネス方針との接続点)。

### 3.7 入力(inputストリーム)

```text
InputHeader {                      // 全入力メッセージ共通の前置
    event_id  : varint
    client_ts : u64
}

KeyEvent {
    header
    down      : bool
    scancode  : u32                // USB HID Usage IDに正規化
    keysym    : u32                // レイアウト解釈済み(0=不明)
    modifiers : u16
}

TextInput      { header, text : string }              // IME確定文字列
ImeComposition { header, text : string, caret : u16 } // 未確定文字列(予約)

MouseMove      { header, x, y : i32 }                 // 仮想デスクトップ物理px
MouseButton    { header, button : u8, down : bool, x, y : i32 }
Wheel          { header, dx, dy : i16, is_precise : bool }  // 高精度ホイール区別
Touch          { header, ... }                        // 予約
```

サーバー側の安全処理: クライアント切断時、押下状態のキー・ボタンをすべて解除する。

### 3.8 フィードバック(feedbackストリーム)

```text
TransportFeedback {
    last_decoded_frame_id   : varint
    last_displayed_frame_id : varint
    receive_bitrate_bps     : u64
    frames_dropped          : u32  // クライアント側で表示せず捨てた数
    decode_delay_us         : u32
    display_delay_us        : u32
    // RTT・損失はQUIC層の統計をサーバー側で取得できるため必須にしない
}
```

送信周期は100ms固定+`last_displayed_frame_id` 変化時。サーバーはこれとQUIC層の `bytes_in_flight`・送信バッファ滞留を合わせて、送信元フレームドロップとエンコーダのレート制御(目標ビットレート、解像度、FPS、キーフレーム間隔、補助レイヤー有無)を判断する。

### 3.9 セッション管理・その他(controlストリーム)

```text
KeepAlive            {}
SessionReauthenticate { reason : enum }        // 再接続・権限再確認時
SessionClose          { reason_code : u16 }
ClipboardFormats      { formats : [FormatId] } // 遅延取得: 一覧のみ通知
ClipboardRequest      { format : FormatId }    // 貼り付け時に実データ要求
FileTransferRequest   { request_id, direction, path, size, ... }
```

クリップボードとファイルの実データは、それぞれ 0x05 / 0x06 ストリーム上で転送し、PermissionSet と個別ポリシー(サイズ・拡張子・保存先制限、監査ログ)を適用する。

## 第7部 矛盾点の是正(第4回レビュー)

現時点のまとめを通読し、記録間で整合が取れていない箇所と、実装不能な欠落を洗い出した。

### 7.1 DisplayCapabilitiesのフィールド所属矛盾

第1部(設計の経緯、3.3節相当)には、`DisplayCapabilities` に `qp_map` `roi_encoding` `b_frames` `intra_refresh` `long_term_reference` を含めると記録されている。ところが第3部のスキーマ本体(3.5節)では、これらのうち `qp_map` `roi_encoding` `intra_refresh` `long_term_reference` の4つが説明なく消えている。

これは単なる書き漏れではなく、そもそも設計として混在していたものを整理した結果であるべきなので、ここで明文化する。

- `qp_map`・`roi_encoding`・`intra_refresh`・`long_term_reference` は、いずれもビットストリームの**符号化側(エンコーダ)**の機能であり、標準準拠のデコーダはこれらを特別な対応なしに復号できる。クライアントが「対応可否」を申告する性質のものではない。
- Tierの判定は、サーバー自身が保有するハードウェアエンコーダの能力に基づいてサーバー側で完結する。クライアントとのネゴシエーションの対象ではない。
- `b_frames` はデコード側のリオーダーバッファ・遅延に直接影響するため、クライアント申告として残す妥当性がある。ただしH.264/HEVCではprofileから機械的に導出できるため、明示フィールドとしては冗長という判断もできる。

**決定**: `DisplayCapabilities` はデコード関連のみ(`codec, profile, bit_depth, chroma_format, max_width, max_height, max_fps, hardware_acceleration`)とし、`b_frames` は独立フィールドにはせず `profile` から解釈する。エンコーダ側機能(qp_map等)はワイヤに一切出さず、`EncoderConfig` の `tier` フィールド(適用結果)のみで表現するという第3部の設計を正式な最終形として確定する。

### 7.2 SessionReauthenticateにreconnect_tokenが無い

再接続の設計方針は「セッションID単独での再接続は禁止、短命・一回限りの reconnect_token を使う」だが、3.9節の `SessionReauthenticate { reason : enum }` にはトークンを運ぶフィールドが存在せず、このままでは再接続処理自体が実行できない。

**決定**: 以下のとおり修正する。

```text
SessionReauthenticate {
    reason           : enum { RECONNECT, PERMISSION_REFRESH, TOKEN_EXPIRING }
    prior_session_id : bytes(16)     // RECONNECT時のみ必須
    reconnect_token  : bytes         // RECONNECT時のみ必須
}
```

成功時、サーバーは新たな `AuthResult`(新 `session_id`・新 `reconnect_token`・`granted_permissions` を再掲)を返す。旧 `reconnect_token` はこの時点で無効化する(一回限りの性質を維持)。失敗時は `AuthResult{status: DENIED}` を返し、QUICコネクションを切断する。

### 7.3 TimeSyncの送信ストリームが未確定

「controlでもfeedbackでもよい」という記述は、送信元によって時刻推定の基準がずれる余地を残す。

**決定**: `TimeSync` は control ストリームに固定する。feedback ストリームでの送信は禁止し、時刻オフセット推定の基準を単一化する。

## 第8部 未決定事項の検討(UX最優先・開発工数を考慮しない)

第5部で挙げた未決定事項、および前節で新たに見つかった設計判断が必要な項目について、開発工数を考慮せずユーザー利便性を最優先にした提案を出し、その提案に対する反駁を経て、採用方式を決定する。

### 8.1 映像ペイロードのビットストリーム形式

**UX優先の提案**: 対応コーデックを絞らず、H.264・HEVC・AV1・将来のVVCまで幅広く対応し、環境ごとに最良の画質を提供する。

**反駁**: 対応コーデックを増やすほど相互運用テストのマトリクスが破綻し、実運用で確実に動くのは結局1系統だけという事態になりやすい。ユーザー体験の本質は「コーデックの豊富さ」ではなく「途切れずに繋がること」であり、コーデックのバリエーションはそこに寄与しない。また可変長コーデックの混在は、パケットロス時のリシンク性(Annex-Bのstart code探索によるリシンク容易性)の観点でも足並みを揃えにくい。

**採用**: 初期版はH.264 Annex-Bを唯一の必須実装とする。HEVC・AV1はTier 2以上の環境向けオプション拡張とし、いずれもAnnex-B(AV1のみOBUネイティブ)で統一する。コーデック選択はサーバーが自動判定し、ユーザーには選ばせない(設定項目を増やさないことがUXに直結する)。

### 8.2 Datagram化(第2段階)の設計

**UX優先の提案**: 低遅延こそ最大のUXなので、初期版から映像もDatagram+LTR/Intra-refreshで送る。

**反駁**: 低遅延だけがUXではない。Datagramは回線が不安定なほどブロックノイズや画面の一時的な崩れを生みやすく、業務用途では「文字が一瞬読めなくなる」実害の方が数十ms程度の遅延増より嫌われることが多い(ゲーム配信と生産性ツールでは優先順位が逆になる)。工数を無視しても、常時低遅延と常時高画質は両立しないトレードオフ自体は消えない。

**採用**: 常時Datagramにはせず、**通常時は信頼性ストリーム、回線劣化を`TransportFeedback`で検知した場合のみDatagram+Intra-refreshへ自動フェイルオーバーする**ハイブリッド方式を採用する。工数を問わないからこそ、両方式を実装した上で自動切替するという贅沢な選択ができる。ベストケースでは画質崩壊ゼロ、ワーストケースでは低遅延優先、の両取りを狙う。

### 8.3 音声転送

**UX優先の提案**: 会議・動画視聴・通知音のために、初期版から低遅延(Opus、20ms程度)の音声転送を実装する。

**反駁**: 音声はマイク・スピーカーのプライバシー影響が大きく、盗聴リスクを伴う新たな権限区分が必要になる。また映像の「送信元フレームドロップ」時に音声との同期がずれる問題が新規に発生し、UX的には「音ズレしたリモート会議」は「音がない」よりも不快な体験になり得る。

**採用**: 音声は初期版スコープに組み込む。専用 `audio` ストリーム(0x07)を新設し、コーデックはOpus固定。権限は `AUDIO_PLAYBACK` / `AUDIO_CAPTURE` を独立ビットとして `PermissionSet` に追加する。同期は映像と同じ単調時計・`capture_ts` 方式を流用し、クライアント側でジッターバッファにより合わせる。

```text
AudioFrame {
    frame_id    : varint
    capture_ts  : u64      // 映像と同じ時計基準
    payload_len : varint
    payload     : bytes    // Opus
}
```

### 8.4 複数モニター同時ストリーム

**UX優先の提案**: マルチモニターは標準構成なので、初期版から全モニターを同時にフルレートでストリーミングする。

**反駁**: 全モニター常時フルレート送信は帯域の無駄が大きく、ユーザーが同時に注視できるのは通常1画面だけである。見ていないモニターを高画質で送り続けると、輻輳制御が見ているモニターの画質を犠牲にし、かえってUXを損なう。

**採用**: 全モニターに対して `video` ストリーム(モニターごとに複数、`DisplayConfig.monitor_id` に対応)を張ること自体は許容するが、**フォーカスされていないモニターは自動的に低FPS・低解像度へ格下げ**する。クライアントは表示中のモニターを `ActiveMonitor` メッセージでサーバーへ通知し、サーバーは帯域をフォーカスモニターへ優先配分する。

```text
ActiveMonitor { monitor_id : u8 }   // controlストリーム、クライアント→サーバー
```

### 8.5 USBリダイレクト

**UX優先の提案**: ドングル認証・外部ストレージ・Webカメラなど利便性が高いため、初期版から全デバイスクラスに対応する。

**反駁**: これは元々「攻撃面が大きい」として慎重論があった領域であり、全デバイスクラス対応はストレージ経由のデータ持ち出しやHIDなりすまし攻撃のリスクを増大させる。これはUXでなくセキュリティの構造的課題であり、工数の多寡とは無関係に軽々しく広げるべきではない。また「無制限USB転送」は多くの組織のセキュリティポリシーと衝突し、結局管理者に無効化されるなら実装しても使われない。

**採用**: デバイスクラス単位の許可制は維持しつつ、UXの摩擦を下げるため**用途プリセット**を追加する。「リモートデスクトップ用途」プリセット(HID・スマートカード・Webカメラのみ許可、ストレージ・プリンタは既定オフ)を用意し、管理者は個別クラスの許可設定を意識せずプリセットを選ぶだけで運用できるようにする。

### 8.6 接続モデル(ランデブー・NAT越え・リレー)

**UX優先の提案**: ポート開放やVPN設定は一般ユーザーにとって最大の導入障壁なので、初期版からP2Pホールパンチング+リレーフォールバックを実装し、接続コードを打つだけで繋がる体験を提供する。

**反駁**: リレー経由を最初から前提にすると、境界内で完結させたいエンタープライズのセキュリティ要求と衝突する。また「誰が運用するリレーを信頼するか」は製品のガバナンス問題であり、工数を無視しても即決できる性質のものではない。初期段階で決め打つと、後の企業向け配布(自前リレー限定運用)がしづらくなる。

**採用**: 初期版から直接接続とリレーの両対応を入れる。ただし既定動作は「直接接続を最優先し、失敗時のみ自組織が運用する(またはセルフホスト可能な)リレーを使う」とし、**匿名の共有リレーへの自動フォールバックは行わない**。UXとしては接続コード・QRコードでの簡易接続を初期版から提供し、直接接続かリレー経由かの切替はユーザーから完全に不可視にする。

### 8.7 MFAの具体方式とエンロールUI

**UX優先の提案**: 摩擦の少ないPasskey/WebAuthn(生体認証)を第一候補にし、QRコードでのモバイル連携エンロールを標準にする。

**反駁**: WebAuthnはプラットフォーム認証器(Windows Hello、Touch ID)に依存し、ブラウザ的なRPの概念をネイティブクライアントに移植するのは見た目より重い。また共有端末・キオスク端末ではプラットフォーム認証器が使えないケースがあり、TOTPの方が扱いやすい場面が残る。

**採用**: WebAuthn/Passkeyを第一推奨、TOTPを必須フォールバックとして**両方標準搭載**する(工数を問わないため両立させる)。エンロールは、管理者が発行した招待QRをユーザーがモバイルでスキャンしその場でPasskey登録する動線を第一候補とし、TOTPの手動登録も並行してサポートする。

### 8.8 Waylandヘッドレス

**UX優先の提案**: 無人アクセスは重要な機能なので、初期版から仮想ディスプレイ+専用wlrootsベースコンポジタを実装し、Windows/macOSと同等の無人アクセス体験を提供する。

**反駁**: 自前の仮想コンポジタ運用は、事実上もう一つのデスクトップ環境を保守することに等しい。GNOME/KDE間のセッション管理・`systemd-logind` 連携・GPU直接アクセスの差異は非常に大きく、工数を無視しても持続可能な設計かどうか自体が疑わしい。加えて、仮想ディスプレイ方式は「ユーザーが普段使っている画面そのもの」への無人アクセスにはならず、体験として本来求められているものとズレる。

**採用**: 独自の仮想コンポジタは作らず、GNOME Remote Desktop等**ディストリビューション標準のリモートデスクトップポータルにSARDPが認証・アクセス制御・監査ログ層として連携**する構成を採る。在席接続はrestore token方式、無人接続はディストリ標準サービスとの統合、という役割分担にする。これは「実際に使っているセッションへの無人アクセス」という本来の目的に最も合致する。

### 8.9 カーソルを除外できないキャプチャ環境

第2回レビューで前提としていた「サーバー映像からカーソルを除外できる」は、古いキャプチャAPIでは保証されない。

**UX優先の提案**: 二重カーソルが出るくらいなら、その環境ではクライアント側描画を無効化し、サーバー側焼き込みカーソルのみに自動フォールバックする。

**反駁**: サーバー側焼き込みにフォールバックすると、その環境だけ体感遅延がRTT分悪化する。環境によって操作感が変わること自体がユーザーの混乱要因になる(あるPCでは軽快、別のPCでは重い)。

**採用**: `EncoderConfig` に `server_cursor_excludable : bool` を追加する。falseの環境では、可能ならサーバー側システムカーソルを最小サイズ・単色に強制変更するAPIを使って目立たなくし、それも不可能なら二重表示を許容する。**操作感の一貫性(常にクライアント側描画による低遅延)を優先**し、視覚的な二重カーソルの方を受け入れる。

```text
EncoderConfig {
    ...(既存フィールド)
    server_cursor_excludable : bool
}
```

### 8.10 IMEの二重入力問題

第3回レビューで採用したクライアント側IME方式は、リモート側アプリが生キーを必要とする場面(IME状態を検知して挙動を変えるアプリ、ネスト接続、ゲーム等)と衝突する可能性がある。

**UX優先の提案**: 最も快適なのはクライアント側でIME変換を完結させ、変換候補も手元で操作できる体験なので、常にクライアント側IME確定文字列(`TextInput`)を優先し、IME関連の生キーはリモートに送らない。

**反駁**: クライアント確定のみに固定すると、リモート側アプリがIME状態そのものを検知して挙動を変える場合(全角/半角の自動切り替えなど)に対応できず、一部のアプリで文字入力そのものが破綻する。

**採用**: **セッション単位で切替可能な2モード制**にする。既定は「クライアントサイドIMEモード」(変換候補表示も手元、体感が軽い)。ユーザーはワンクリックで「リモートサイドIMEモード」に切替可能とし、切替時は生の `KeyDown`/`KeyUp`/IME関連キーをすべてリモートに転送し、クライアント側は `TextInput` を送らない。モードはセッション単位で排他的とし、切替の瞬間に入力キューをフラッシュして二重入力を防ぐ。

```text
ImeModeChange {
    mode : enum { CLIENT_SIDE, REMOTE_SIDE }
}
```

### 8.11 ライブ権限変更(降格)

強制切断だけでなく、管理者が接続を切らずに権限を即座に絞れる方が業務を止めずに済む。

**UX優先の提案**: `PermissionUpdate` を新設し、管理者操作でいつでも即座に権限を反映する。

**反駁**: 進行中の `file`/`clipboard` 転送を即座に打ち切ると、ユーザーからは「転送が突然失敗した」としか見えず分かりにくい。強制切断+再接続の方が「何が起きたか」が明確という見方もできる。

**採用**: `PermissionUpdate` を追加するが、**降格時は進行中の転送を完了まで許容し、新規開始のみ禁止**する。一方で `INPUT_KEYBOARD`/`INPUT_MOUSE` の停止など即時性が要る項目は `effective_immediately: true` で即座に反映する。段階的適用により、両者の懸念を両立させる。

```text
PermissionUpdate {
    granted_permissions     : PermissionSet
    effective_immediately   : bool   // true: 入力系など即時遮断が必要な項目向け
                                     // false: file/clipboard等、進行中処理は完了まで許容
}
```

### 8.12 スキーマファイル化とパーサーファジングのCI組み込み

**UX優先の提案(工数無視のため即決)**: FlatBuffers等での正式スキーマファイル化と、`cargo-fuzz`/`libFuzzer` によるパーサーファジングを初期版から必須プロセスとする。

**反駁**: 通常であれば「初期プロトタイピングの速度が落ちる」という開発上のデメリットがあるが、今回は工数を考慮しない前提のため、この反駁は採用しない。

**採用**: 初期版から必須とする。CIにファジングを組み込み、スキーマ変更のたびに自動実行する。

## 第9部 第7・8部を反映したスキーマ差分まとめ

| メッセージ / フィールド | 変更内容 |
|---|---|
| `DisplayCapabilities` | `qp_map`/`roi_encoding`/`intra_refresh`/`long_term_reference`/`b_frames` を含めないことを正式確定(§7.1) |
| `SessionReauthenticate` | `prior_session_id`・`reconnect_token` フィールドを追加(§7.2) |
| `TimeSync` | control ストリーム限定に確定(§7.3) |
| `AudioFrame`(新規) | `audio` ストリーム(0x07)、Opus固定(§8.3) |
| `PermissionSet` | `AUDIO_PLAYBACK`/`AUDIO_CAPTURE` を追加(§8.3) |
| `ActiveMonitor`(新規) | フォーカスモニール通知、帯域優先配分に使用(§8.4) |
| `EncoderConfig` | `server_cursor_excludable : bool` を追加(§8.9) |
| `ImeModeChange`(新規) | クライアント/リモートIMEモードの排他切替(§8.10) |
| `PermissionUpdate`(新規) | ライブ権限変更、即時/段階適用の使い分け(§8.11) |
| ストリームプロローグ | `0x07 audio` を追加 |

これにより、第3部までの初期版スコープは以下のとおり拡張される。

- 音声転送(Opus)を初期版に含める
- 複数モニターの適応的な帯域配分
- USB用途プリセット
- 直接接続+自組織リレーの両対応
- WebAuthn/Passkey + TOTPの併用MFA
- Waylandはディストリ標準ポータル連携方式
- カーソル二重表示の許容基準
- IMEの2モード切替
- ライブ権限変更

未決定事項(第5部)のうち、映像ビットストリーム形式・Datagram化の詳細設計は本改訂で方針を確定した。残る主要な将来課題は「FlatBuffers定義ファイルそのものの記述」「VVC等コーデックの追加時期」「エンタープライズ向けリレーの具体的な運用モデル(誰が鍵管理をするか)」の3点に絞られる。

## Errata(v0.3時点)

本ファイルは設計史ジャーナルとして、当時の議論をそのまま保存する。以下の記述は後の版で更新されているため、実装の参照は必ず最新の規範仕様(`sardp-normative-spec-v0.3.md`)を用いること。

- **第4部 4.1「映像ストリームは長寿命1本で確定」「フレームごとのストリーム生成とRESETは第2段階で検討」**: v0.2/v0.3で、バックログが臨界値を超えた場合にストリーム全体をRESET_STREAM+再オープンする回復機構(generation管理付き)として正式化された。ここで棄却したのは「通常運用中に個々のフレームを間引く」案であり、両者は矛盾しない。
- **第8部 8.11 `PermissionUpdate { effective_immediately : bool }`**: v0.2で `immediate_revoke : PermissionSet` 方式に置き換えられた。権限ごとに即時/段階を分けられない bool 案は棄却済み。
- **第8部 8.3 音声「専用audioストリーム(0x07)」**: v0.2で `audio_playback`(0x07、server→client)と `audio_capture`(0x08、client→server)の2種類に分割された。
- **第9部の `TimeSync { t1, t2, t3 }`(どちらのストリームでも可)**: v0.2で `control` ストリーム固定に確定し、`TimeSyncRequest`/`TimeSyncResponse` の2メッセージに分割された(v0.3でRFC相当の計算式も確定)。
